# 매크로 대시보드 개발 원칙

이 문서는 이 프로젝트에서 코드를 작성·수정하는 모든 에이전트(개발/리뷰/평가)가 따르는 기준이다.

---

## 1. 코딩하기 전에 먼저 판단하라

가정하지 마라. 혼란을 숨기지 마라. 선택지와 트레이드오프를 드러내라.
구현을 시작하기 전에 다음을 수행하라.

- 네가 전제한 가정을 명시하라.
- 불확실한 부분이 있으면 질문하라.
- 해석이 여러 개 가능하다면 조용히 하나를 고르지 말고 가능한 해석들을 제시하라.
- 더 단순한 접근이 있다면 먼저 말하라.
- 사용자의 요구가 과하거나 방향이 잘못되었다고 판단되면 근거를 들어 반박하라.
- 명확하지 않은 부분이 있으면 멈춰라.
- 무엇이 헷갈리는지 정확히 이름 붙여라.
- 필요한 질문을 먼저 하라.

## 2. 단순함을 우선하라

요구사항을 해결하는 최소 코드만 작성하라. 추측성 기능을 넣지 마라.

- 요청받지 않은 기능을 추가하지 마라.
- 한 번만 쓰이는 코드에 추상화를 만들지 마라.
- 요구되지 않은 유연성, 설정 옵션, 확장성을 넣지 마라.
- 실제로 발생할 수 없는 상황을 위한 에러 처리를 만들지 마라.
- 50줄로 해결할 수 있는 코드를 200줄로 작성했다면 다시 줄여라.

항상 다음 기준으로 점검하라.
"시니어 엔지니어가 이 코드를 보고 과하게 복잡하다고 말할 것인가?"
대답이 "그렇다"라면 단순화하라.

## 3. 최소 변경안을 염두하라

반드시 필요한 부분만 수정하라. 네 변경으로 생긴 찌꺼기만 정리하라.
기존 코드를 수정할 때 다음을 지켜라.

- 관련 없는 코드를 개선하지 마라.
- 인접 코드, 주석, 포맷을 임의로 정리하지 마라.
- 고장 나지 않은 코드를 리팩터링하지 마라.
- 기존 스타일이 마음에 들지 않아도 현재 코드베이스의 스타일을 따라라.
- 관련 없는 죽은 코드를 발견하면 삭제하지 말고 사용자에게 언급만 하라.

네 변경으로 인해 불필요해진 코드가 생기면 다음을 수행하라.

- 네 변경 때문에 unused 상태가 된 import, 변수, 함수는 제거하라.
- 기존에 이미 존재하던 죽은 코드는 요청받지 않았다면 제거하지 마라.

모든 변경 라인은 다음 질문을 통과해야 한다.
"이 줄은 사용자의 요청과 직접 연결되는가?"
직접 연결되지 않는다면 수정하지 마라.

## 4. 목표 중심으로 실행하라

성공 기준을 먼저 정의하고, 검증될 때까지 반복하라.
작업을 검증 가능한 목표로 바꿔라.

- "validation 추가" → "잘못된 입력에 대한 테스트를 작성하고, 그 테스트를 통과시켜라."
- "버그 수정" → "버그를 재현하는 테스트를 먼저 작성하고, 그 테스트를 통과시켜라."
- "X 리팩터링" → "리팩터링 전후로 테스트가 모두 통과하는지 확인하라."

여러 단계가 필요한 작업은 시작 전에 짧은 계획을 제시하라.

```
1. [작업 단계] → 검증: [확인 방법]
2. [작업 단계] → 검증: [확인 방법]
3. [작업 단계] → 검증: [확인 방법]
```

강한 성공 기준은 독립적으로 작업을 반복하고 마무리할 수 있게 한다.
약한 성공 기준, 예를 들어 "작동하게 만들어라" 같은 표현은 계속 사용자 확인을 요구하게 만든다.
이런 경우에는 먼저 성공 기준을 구체화하라.

## 5. 데이터 파이프라인 규칙 (이 프로젝트 고유)

매일 도는 데이터 수집은 LLM이 아니라 결정론적 파이썬 모듈이 담당한다.

- 각 페처 모듈은 **한 도메인만** 담당한다 (금리 / 유동성 / 위험선호 / 물가·고용 / 시장가격).
- 각 모듈의 입력은 고정된 series ID 목록, 출력은 정해진 스키마의 JSON이다.
- 네트워크 실패나 키 부재 시 **샘플 데이터로 폴백**하고, 실패 사실을 데이터에 기록한다(조용히 넘어가지 마라).
- 지표를 추가할 때는 새 모듈을 만들지 말고 해당 도메인 모듈의 series 목록에만 추가한다.
- 조립(build) 단계와 수집(fetch) 단계를 섞지 마라.

## 6. 리뷰 가드레일

리뷰 에이전트는 다음을 특히 감시한다.

- **잘 돌던 코드를 통째로 갈아엎는 변경**을 막는다. 큰 삭제/재작성은 반드시 근거를 요구한다.
- diff가 요청 범위를 벗어나면 지적한다(원칙 3 위반).
- 데이터 스키마가 프론트엔드 기대와 어긋나지 않는지 확인한다.
- 해석문의 사실관계가 강의노트 근거와 맞는지 확인한다.

## 7. 커밋/푸시 흐름

- 평가(evaluator) 에이전트가 성공 기준(데이터 로드 OK, 대시보드 렌더 OK)을 통과 처리한 뒤에만 커밋한다.
- 커밋 메시지는 무엇을·왜 바꿨는지 한 줄로 명확히 쓴다.
- 사용자가 요청했을 때만 push 한다. 기본 브랜치라면 먼저 브랜치를 만든다.

## 8. 해석문(설명) 작성 원칙

지표 카드의 해석 텍스트는 다음 3단 구조를 따른다.

1. **일반적 의미** — 이 지표가 무엇을 말하는가 (강의노트 근거).
2. **읽는 법** — 오를 때 / 내릴 때 각각 무엇을 뜻하는가.
3. **현재 상황** — 최신 데이터 기준 지금은 어느 쪽인가 (가능하면 규칙 기반 자동 판정).

한국어로 쓰되, 강의노트의 표현과 논리를 최대한 살린다. 과장하거나 투자 조언으로 단정하지 않는다.
